# Лабораторная 5 · Ответы по документам с проверкой

**Лекция:** 5 · **Сдача:** папка `lab05/` в вашем репозитории: `run.py`, артефакты в `artifacts/`, README из трех разделов по регламенту · **Проверка:** автотесты в CI.

## Задача

На лекции приложение на языковой модели свелось к одной схеме: код находит нужные куски документов, собирает из них промпт, модель отвечает, код проверяет ответ. Модель в этой схеме одна и занимает одно звено, остальное пишете вы. В этой работе вы собираете эту схему целиком на маленькой модели и измеряете, что дает каждое звено.

Задача: ответить на вопросы по материалам этого курса. Корпус это заметки к лекциям 1–4, задания лабораторных 1–4, ТЗ курсовой, регламент лабораторных и README репозитория. Вопросов 40, у каждого короткий эталонный ответ: число, имя модели, название файла, термин. На 10 вопросов из 40 ответа в корпусе нет, и правильный ответ на них это отказ «нет данных». Корпус выбран не случайно: этих фактов нет в весах модели, поэтому по каждому ответу видно, взят он из найденного текста или выдуман.

Модель одна на все три прогона: чат-версия `Qwen/Qwen3-0.6B`, режим размышлений выключен. Для поиска тот же энкодер, что в лабораторной 2: `intfloat/multilingual-e5-small`.

Три прогона на одном наборе вопросов:

1. **Без поиска.** Модель получает только вопрос.
2. **С поиском.** Перед вызовом код находит пять ближайших к вопросу фрагментов корпуса и кладет их в промпт.
3. **С поиском и проверкой.** То же, и после каждого ответа модель отвечает на тот же вопрос второй раз, видя только тот фрагмент, на который сослалась. Если второй ответ не совпал с первым, код заменяет ответ отказом.

Сводная таблица на три строки это главный результат работы.

**Данные.** Два файла в репозитории курса, папка `assignments/05/data/`:

- `corpus.json`: снимок материалов курса на день выдачи работы, поле `documents` это список из 11 документов `{"doc": путь к файлу, "text": текст в Markdown}`. Снимок не меняется, даже если сами материалы потом правятся.
- `questions.json`: список из 40 вопросов. У каждого поля `id`, `question`, `answerable` (есть ли ответ в корпусе), `answers` (список допустимых написаний эталонного ответа, у вопросов без ответа пустой) и `evidence` (фраза из корпуса, рядом с которой стоит ответ; у вопросов без ответа `null`).

```json
[
  {
    "id": 1,
    "question": "Какой энкодер используется для поиска во второй лабораторной?",
    "answerable": true,
    "answers": ["multilingual-e5-small"],
    "evidence": "маленький энкодер для поиска"
  },
  {
    "id": 2,
    "question": "Сколько часов отведено на шестую лабораторную?",
    "answerable": false,
    "answers": [],
    "evidence": null
  }
]
```

Скрипт скачивает оба файла сам по ссылкам `https://raw.githubusercontent.com/pmenshih/tgo-course/main/assignments/05/data/corpus.json` и `.../questions.json` и кладет рядом с собой в `lab05/data/`. В свой репозиторий их коммитить не нужно, добавьте `lab05/data/` в `.gitignore`. Если сеть недоступна, папку с файлами можно передать путем: `python run.py --data путь` или переменной `LAB_DATA`.

Обучения в работе нет, видеокарта не нужна. Полный прогон на процессоре занимает около получаса, на видеокарте несколько минут; в режиме `--fast` несколько минут на процессоре.

## Для курсовой

Тема 1 курсовой называется «Ассистент по корпусу документов с проверкой ответов», и ее метрики это ровно три числа этой работы: точность ответов, доля выдуманных ответов, доля верных отказов на вопросы без ответа в корпусе. Если ваша тема первая, `run.py` из этой работы на вашем корпусе это модуль инференса курсовой, `questions.json` это образец для папки `eval`, а таблица на три строки это раздел результатов.

Если тема другая, из работы всё равно уезжают три вещи. Тестовый набор с эталонами и с запросами, на которые сервис должен отказать, обязателен в любой теме (раздел 2.1 ТЗ). Повторный вызов модели, после которого решение принимает код, это проверка, которая встает после генерации в темах 4, 6 и 7. И оркестрация своим кодом, без фреймворков-обвязок (раздел 2.5): в этой работе видно, что это около двухсот строк.

## Что сделать

Работа это один файл `lab05/run.py`, который проходит пять шагов и пишет артефакты.

1. **Фрагменты.** Разбить каждый документ корпуса на фрагменты по базовому правилу. Документ делится на блоки по пустым строкам. Блок, который начинается с `#`, это заголовок: сам он фрагментом не становится, а запоминается как текущий заголовок для следующих блоков. Соседние блоки под одним заголовком склеиваются в один фрагмент, пока в нем не больше 120 слов (слова считаются разбиением по пробелам); блок длиннее 120 слов идет отдельным фрагментом целиком, резать его не нужно. У фрагмента три поля: документ, текущий заголовок, текст. По этому правилу из корпуса получается около двухсот фрагментов. Записать `chunks.json`.

2. **Поиск.** Функция `search(query, k)` из лабораторной 2 на новом корпусе: каждый фрагмент превращается в вектор энкодером e5 (префикс `passage: `, перед текстом фрагмента его заголовок, среднее выходов по маске, обрезка до 512 токенов энкодера), вопрос в вектор с префиксом `query: `, близость по косинусу. Для каждого вопроса найти пять ближайших фрагментов. Для вопросов с ответом посчитать попадание: есть ли среди пяти найденных фрагмент, в тексте которого встречается фраза `evidence`. Это та же проверка подстрокой, что `answer_id` в лабораторной 2, и модель для нее не нужна. Записать `retrieval.json` с долей попаданий.

3. **Промпт и разбор ответа.** Шаблон чата `Qwen3` через `tokenizer.apply_chat_template` с `enable_thinking=False`, жадная генерация, не больше 64 новых токенов. Системная инструкция своя для каждого прогона, но с общими правилами: ответ коротко, одной строкой JSON вида `{"answer": "...", "source": номер}`; если ответа нет, в поле `answer` стоит «нет данных», а `source` равен `null`. В прогоне без поиска поле `source` всегда `null`. В прогоне с поиском фрагменты идут в сообщении пользователя пронумерованным списком от 1 до 5, после них вопрос; в `source` модель ставит номер фрагмента, из которого взят ответ. Ответ модели разбирается как JSON; если разобрать не удалось, запись попадает в счетчик `invalid` и считается выдуманным ответом. Посчитать среднюю длину промпта в токенах для каждого прогона функцией `count_tokens` из лабораторной 2.

4. **Проверка.** Спрашивать модель, верен ли ее ответ, бесполезно: на лекции было видно, что маленькая модель на такой вопрос отвечает «да» почти всегда. Поэтому проверка устроена иначе: модель делает ту же узкую работу второй раз, а решение принимает код. Для каждого ответа из прогона с поиском, который не является отказом, сделать второй вызов модели с той же системной инструкцией и тем же вопросом, но в промпте оставить один фрагмент: тот, номер которого модель поставила в `source`. Вердикт «да», если второй ответ разобрался как JSON, не является отказом и совпал с первым; ответы совпадают, если после нормализации из пункта 5 один входит в другой как подстрока. Во всех остальных случаях вердикт «нет». Если в первом ответе `source` пуст или номера нет среди пяти фрагментов, вердикт «нет» без второго вызова. Вердикт «нет» значит, что ответ помечен; помеченный ответ в третьем прогоне заменяется на «нет данных», остальные переходят без изменений. Отказы и ответы, которые не разобрались, не проверяются. Эталонные ответы в проверке не участвуют: в работающем сервисе их нет.

5. **Метрики и выводы.** Ответ и эталон сравниваются после нормализации: нижний регистр, «ё» заменяется на «е», из строки убирается все, кроме букв и цифр. Ответ верный, если хотя бы одно написание из `answers` после нормализации входит в него как подстрока. Отказ это ответ, который после нормализации содержит «нетданных». По каждому прогону четыре доли:
   - `correct`: доля вопросов с ответом, на которые ответ верный;
   - `fabricated`: доля всех вопросов, на которые дан неверный ответ, не отказ; сюда попадает любой ответ на вопрос без ответа в корпусе;
   - `refusal_correct`: доля вопросов без ответа, на которые модель отказалась;
   - `refusal_wrong`: доля вопросов с ответом, на которые модель отказалась.

   Отдельно качество проверки, по проверенным ответам. Положительный класс это выдуманный ответ в прогоне с поиском. Точность (`precision`): какая доля помеченных ответов действительно выдумана. Полнота (`recall`): какая доля выдуманных ответов помечена.

   После проверки `refusal_wrong` вырастет, и это не ошибка: неверный ответ на вопрос с ответом, который проверка заменила отказом, переходит из выдуманных в отказы. Смотреть нужно на все четыре доли вместе.

   В README таблица на три строки и ответы на четыре вопроса. Что дал поиск и чем за это заплачено в токенах промпта. На каких вопросах поиск нашел нужный фрагмент, а модель всё равно ответила неверно, и что у этих вопросов общего. Что модель отвечает на вопросы без ответа в корпусе, когда ближайшие фрагменты нашлись, и откуда она берет этот ответ. Сколько верных ответов проверка забраковала и сколько выдуманных пропустила, и стоит ли при таких числах ставить ее в сервис.

## Контракт для тестов

`lab05/run.py` запускается из любой папки, без аргументов делает полный прогон (40 вопросов), с флагом `--fast` укладывается в десять минут на процессоре: корпус целиком и первые 10 вопросов набора, среди которых три без ответа. Все пути считаются от папки скрипта. Артефакты в `lab05/artifacts/`; образцы всех файлов из полного прогона лежат в `assignments/05/examples/`, числа будут свои.

| Файл | Содержимое |
|---|---|
| `chunks.json` | список фрагментов в порядке корпуса, каждый `{"id": номер с нуля, "doc": путь документа, "heading": текущий заголовок или пустая строка, "text": текст}` |
| `retrieval.json` | `encoder`, `k` (5), `questions`: список `{"id", "top": номера фрагментов по убыванию близости, "scores": косинусы, "hit": true, false или null у вопросов без ответа}`; `hit_rate`: доля попаданий среди вопросов с ответом |
| `answers.csv` | колонки `id`, `answerable`, `no_search`, `rag`, `rag_source`, `verdict`, `rag_verified` и сырые ответы модели `raw_no_search`, `raw_rag`, `raw_verifier`; в колонках прогонов поле `answer` из разобранного JSON или пусто, если разобрать не удалось; `verdict` это `да`, `нет` или пусто у отказов и неразобранных ответов; `raw_verifier` это сырой ответ модели на повторный вопрос, пусто, если второго вызова не было |
| `metrics.json` | `model`, `encoder`, `fast`, `k`, `n_questions`, `n_unanswerable`, `n_chunks`, `modes`: для каждого из `no_search`, `rag`, `rag_verified` словарь с `correct`, `fabricated`, `refusal_correct`, `refusal_wrong`, `invalid`, `prompt_tokens`, `sec_per_question`; `verifier`: `checked` (сколько ответов проверено), `flagged` (сколько помечено), `precision`, `recall` |

Тесты числам, которые скрипт записал о себе, не верят и пересчитывают, что могут:`

- `chunks.json`: фрагментов не меньше 100; текст каждого фрагмента встречается в документе `doc` корпуса (сравнение без учета пробелов и переводов строк); фрагментов длиннее 300 слов нет.
- `retrieval.json`: у каждого вопроса ровно `k` номеров в пределах числа фрагментов; `hit` пересчитывается поиском `evidence` в текстах найденных фрагментов; `hit_rate` пересчитывается и не ниже порога из эталона.
- `answers.csv`: строк столько же, сколько вопросов в прогоне; четыре доли по каждому прогону пересчитываются по эталонам из `questions.json` и сверяются с `metrics.json`; `rag_verified` совпадает с `rag` там, где вердикт «да» или пусто, и равен «нет данных» там, где вердикт «нет»; сам вердикт пересчитывается по `rag` и `raw_verifier`; точность и полнота проверки пересчитываются.
- Качество: `correct` в прогоне с поиском выше, чем без поиска, не меньше чем на порог из эталона (`tests/data/lab05/thresholds.json`); в `--fast` порог ниже, и в CI проверяется именно он. Три прогона дают не одинаковые ответы на все вопросы.

Качество проверки порогом не ограничено: какие у нее точность и полнота на маленькой модели, это предмет вашего README, а не условие сдачи.

Если какой-то тест кажется неверным, пишите сразу, не подгоняйте под него результат.
