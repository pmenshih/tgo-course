# ТГО — курсовая

## 1. Цель работы

Разработать сервис на основе языковой модели, который решает конкретную прикладную задачу и состоит как минимум из трех взаимодействующих модулей. Сервис должен запускаться одной командой, отвечать через пользовательский интерфейс, хранить данные, вести учет экспериментов и собирать метрики своей работы.

Главный принцип: модель делает узкую работу, остальное делает код.

## 2. Требования к сервису

### 2.1. Функциональные

- Сервис решает поставленную задачу с помощью языковой модели: предобученной, предобученной с RAG или дообученной.
- Пользователь получает ответ через интерфейс: веб-интерфейс, Telegram-бот или CLI.
- Сервис логирует каждый запрос и ответ, время ответа и объем сгенерированных токенов в базу данных.
- Сервис имеет тестовый набор не менее чем из 30 запросов с эталонными ответами и скрипт, который прогоняет набор и считает метрику качества. Для RAG-тем в наборе должны быть запросы, на которые ответа в документах нет.
- Эксперименты (не менее двух сравниваемых конфигураций: модель, промпт, параметры retrieval, параметры генерации) зафиксированы в MLflow с параметрами и метриками.
- Сервис запускается одной командой на машине без GPU.

### 2.2. Нефункциональные

- Код в Git, репозиторий на GitHub, история коммитов отражает ход работы, а не один коммит в конце.
- Код документирован: docstring у публичных функций, типизация, комментарии там, где решение неочевидно.
- README содержит: описание задачи и данных, схему архитектуры, инструкцию по запуску, примеры запросов (скриншоты или curl), структуру репозитория, результаты экспериментов, ограничения и известные проблемы.
- Схема архитектуры (Mermaid или draw.io) показывает компоненты, протоколы взаимодействия и обосновывает выбор технологий.
- Секреты (токены ботов, ключи API) не хранятся в репозитории, передаются через переменные окружения с примером в `.env.example`.

### 2.3. Состав модулей

Типовая структура:
1. **Интерфейс.** Веб-интерфейс, Telegram-бот или CLI. Принимает запрос, показывает ответ, при необходимости источники и служебную информацию. С модулем инференса общается только через HTTP-API, а не импортирует его код напрямую.
2. **Инференс.** Отдельный сервис (FastAPI), который загружает модель или обращается к серверу модели (Ollama, vLLM, llama.cpp), выполняет промптинг, retrieval, вызов инструментов и возвращает структурированный ответ.
3. **Хранение.** Реляционная БД (PostgreSQL, SQLite) для логов запросов и пользовательских данных. Для RAG дополнительно векторное хранилище (ChromaDB, Qdrant, pgvector).
4. **Учет экспериментов и мониторинг.** MLflow для экспериментов плюс простая панель или эндпоинт с текущими метриками сервиса: число запросов, среднее и 95-й перцентиль времени ответа, доля отказов, расход токенов.

Все четыре компонента должны быть выделены явно, состав внутри каждого может меняться под тему.

### 2.4. Ограничения на модель

- Основная языковая модель: не более 4 миллиардов параметров. Ориентиры: Qwen3-4B, Qwen3-1.7B, Gemma-3-4B, Phi-4-mini и аналоги. Допустима и приветствуется квантизация (GGUF Q4–Q8).
- Модель эмбеддингов для RAG: не более 600 миллионов параметров (multilingual-e5-small/base, bge-m3 и аналоги).
- Веса модели в репозиторий не кладутся: модель скачивается автоматически при первом запуске (Hugging Face Hub, `ollama pull` в entrypoint контейнера). Проверяющий не должен искать веса вручную.
- Сервис на CPU с 16 ГБ оперативной памяти отвечает на типовой запрос не дольше 120 секунд. Время ответа указывается в README.
- Облачные API (OpenAI, Anthropic, Yandex, GigaChat) допускаются только как необязательный компонент: сервис работает без них на локальной модели, а при использовании API необходимо показать стоимость запроса и фолбэк на локальную модель.
- Дообучение (SFT/PEFT) выполняется на Kaggle или Colab, в сервисе используется уже обученный адаптер LoRA либо модель с вмерженным адаптером, сконвертированная в GGUF. Обучение проверяется по артефактам, а не перезапуском: ноутбук сдается с сохраненными выводами ячеек, параметры и метрики обучения записаны в MLflow, дообученная модель сравнивается с базовой на тестовом наборе в самом сервисе.

### 2.5. Рекомендуемый стек

- Python 3.11+.
- Инференс: Ollama, llama.cpp или vLLM.
- RAG и агенты: собственный код. Оркестрация (разбиение на чанки, поиск, сборка промпта, цикл вызова инструментов) пишется самостоятельно, фреймворки-обвязки (LangChain, LlamaIndex, Haystack и аналоги) не используются. Клиентские библиотеки моделей, векторных баз и эмбеддингов (openai, ollama, chromadb, qdrant-client, sentence-transformers) использовать можно.
- Дообучение: PEFT и TRL.
- API: FastAPI.
- Интерфейс: на выбор.
- Хранение: PostgreSQL, SQLite, ChromaDB, Qdrant, pgvector, Redis.
- Эксперименты: MLflow.
- Контейнеризация: Docker, Docker Compose.

Стек рекомендуемый. Замена на аналог допускается при обосновании в README.

## 3. Темы

Все темы построены вокруг языковой модели. Классические задачи (временные ряды, рекомендации, компьютерное зрение) возможны через тему 10, если в сервисе есть модуль на языковой модели.

1. **Ассистент по корпусу документов с проверкой ответов.** RAG по выбранному корпусу (документация, учебные материалы, нормативные акты). Второй проход проверяет ответ против найденных фрагментов и помечает утверждения без опоры на источник. Метрики: точность ответов, доля галлюцинаций, доля верных отказов на вопросы без ответа в корпусе.

2. **Агент с инструментами над структурированными данными.** Пользователь задает вопрос на естественном языке к базе данных или внешнему API, модель порождает вызов инструмента (SQL-запрос, параметры запроса к API), код его исполняет и проверяет, модель формулирует ответ. Метрики: доля корректно исполненных запросов, точность ответов на тестовом наборе вопросов.

3. **Сервис на дообученной модели под узкую задачу.** Модель до 4B дообучается через PEFT на задачу структурированного извлечения или классификации (разбор обращений в поддержку, извлечение полей из документов, разметка товаров,..). Сервис сравнивает дообученную модель с базовой в zero-shot и few-shot режимах. Метрики: F1 или точность извлечения, время ответа, потребление памяти. 

4. **Автоматическая разметка данных с контролем качества.** Модель размечает неразмеченный набор текстов, вторая модель или та же с другим промптом оценивает уверенность, спорные примеры уходят в очередь на ручную проверку через интерфейс. Метрики: согласие с ручной разметкой на контрольной выборке, доля примеров, отправленных на ручную проверку.

5. **Мониторинг текстового потока.** Сервис забирает поток текстов (новости по теме, отзывы, обращения), извлекает сущности и темы, группирует близкие сообщения и формирует дайджест по расписанию. Метрики: качество извлечения сущностей на размеченной выборке, качество дайджеста по оценке LLM-as-judge с ручной проверкой части оценок.

6. **Генератор учебных заданий.** По учебному материалу сервис порождает вопросы с вариантами ответов и пояснениями, проверяет, что правильный ответ опирается на текст материала, и отбраковывает задания без опоры. Метрики: доля заданий, принятых экспертом без правок, доля отбракованных проверкой.

7. **Служба поддержки с маршрутизацией.** Входящее обращение классифицируется, типовые вопросы получают ответ по базе знаний, нетиповые или рискованные уходят оператору с кратким резюме и предложенным ответом. Метрики: точность классификации, качество ответов по базе знаний, доля верных эскалаций.

8. **Защитный контур для языковой модели.** Сервис-прослойка перед моделью: обнаружение инъекций промпта, персональных данных и запросов вне тематики, фильтрация ответа, журнал инцидентов. Тестовый набор включает собственную коллекцию атак. Метрики: precision и recall детектора на наборе атак и обычных запросов, добавленная задержка. Связана с «охотой за поломками».

9. **Стенд для оценки LLM-систем.** Сервис принимает конфигурацию системы (модель, промпт, параметры retrieval), прогоняет тестовый набор, оценивает ответы через LLM-as-judge и эталоны, пишет результаты в MLflow и показывает сравнение конфигураций. Метрики: согласие судьи с ручной оценкой, воспроизводимость результатов между прогонами.

10. **Своя тема.** Задача из рабочего проекта, выпускной квалификационной работы или собственного интереса. Согласовывается с преподавателем, должна укладываться в требования раздела 2.

Работа индивидуальная. Команда допускается по согласованию, если в README явно разделено, кто какие модули делал, при этом каждый защищает свою часть.

## 4. Состав сдаваемого

Отдельный текстовый отчет не сдается, его роль выполняет README. Репозиторий содержит:
- код всех модулей;
- `Dockerfile` для каждого сервиса и `docker-compose.yml`;
- `requirements.txt` или `pyproject.toml`;
- `.env.example`;
- `README.md` по требованиям раздела 2.2;
- схему архитектуры (изображение плюс исходник Mermaid или .drawio);
- тестовый набор и скрипт оценки в папке `eval`;
- ноутбуки с экспериментами и дообучением в папке `notebooks`;
- экспорт экспериментов MLflow или скриншоты;
- скриншоты работы сервиса в папке `screenshots` или в README.

## 5. Использование ИИ-ассистентов

Пользоваться ассистентами можно и нужно, это часть профессии. Три правила курса действуют и здесь:
1. Вы отвечаете за каждую строку. На защите объясняете и меняете свой код без ассистента.
2. Перепроверяйте модель. Это относится и к ассистенту, и к модели внутри сервиса.
3. Не теряйте свой проект. Ассистент помогает думать, а не думает за вас.

## 6. Защита

Порядок:
1. Задача и метрика. Какую задачу решает сервис, как измеряли успех, какие результаты на тестовом наборе.
2. Живая демонстрация. Показ нескольких запросов, в том числе один неудобный для модели.
3. Архитектура. По схеме: какие модули, как взаимодействуют, почему выбраны эти технологии.
4. Эксперименты. Что сравнивали, что выбрали и почему, данные из MLflow.
5. Код. Нужно объяснить произвольный файл и внести небольшое изменение без ассистента.

Критерии оценки:

| Критерий                                                                                             | Вес  |
| ---------------------------------------------------------------------------------------------------- | ---- |
| Сервис работает: запускается одной командой, отвечает через интерфейс, выдерживает неудобные запросы | 30 % |
| Качество измерено: тестовый набор, метрика, честное обсуждение ошибок                                | 20 % |
| Архитектура и инженерия: модули, интерфейсы, хранение, мониторинг, качество кода и README            | 20 % |
| Эксперименты: сравнение конфигураций, выводы, фиксация в MLflow                                      | 15 % |
| Владение кодом на защите                                                                             | 15 % |

Если вы не можете объяснить и изменить свой код на защите, работа не принимается независимо от остальных критериев.
